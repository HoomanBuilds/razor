## Operations

Run these commands over the existing SSH connection to `ubuntu@15.135.178.84`:

```sh
sudo systemctl status razor-web razor-worker razor-demo
sudo journalctl -u razor-web -u razor-worker --since '10 minutes ago' --no-pager
curl --fail https://razorfi.xyz/api/health
sudo systemctl restart razor-web razor-worker razor-demo
```

Keep secrets in the protected environment file. Restart the web and worker services after changing production server configuration; the demo does not read that file. Restart all three after switching application code. Changes to `NEXT_PUBLIC_*` values require a fresh application build. Preserve the data-encryption key; replacing it does not re-encrypt stored records.

For a future release, prepare one memory-capped build, transfer it to a new release directory, install matching ARM64 dependencies and verify configuration. Before activating code that changes storage, stop the Razor services and create a consistent database backup with the original encryption key retained separately. Atomically replace the `current` symlink, then restart all three services and verify both health endpoints and the actual browser flow. Do not run multiple workers against different release versions during migration.

Keep the prior release until the new version is verified, subject to available disk space. A code rollback is safe only when the previous version supports the current database schema. Do not rewind the database after new payments or other records have been created. The prior hosted release remains available at `/opt/razor/releases/4ed6357a10cc`. The current update did not change the database schema. The original shared Caddy configuration is retained at `/etc/caddy/Caddyfile.before-razor`; remove only Razor's import to detach this application without changing other sites.

The imported local snapshot is not an ongoing production backup. Scheduled off-server database backups and restore drills have not been configured by this deployment.
